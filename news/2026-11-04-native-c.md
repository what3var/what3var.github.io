---
title: The native backend speaks C - and can be debugged
tag: Native
---
`forge build --engine native` turns a fire program into a native executable, and that backend has been rebuilt from the ground up: it now writes plain C11 instead of C++, leaves out the code a program never reaches, can be debugged from spark like the VM, and builds libraries once instead of every time.

![spark debugging a natively compiled program: the engine box says Native, the program is paused at a breakpoint and the Scope panel shows its variables](news/native-debug.png)

- **C11 instead of C++.** The generated code and the runtime (`fire_rt.h`) are plain C, and so are the standard packages - JSON, hash, compression, circuits, graphics, windows, scene3d. Programs build with gcc, clang, TinyCC, MinGW, Emscripten and ESP-IDF. Most of the benchmarks got faster on the way - up to 30 % for short programs, mostly because a C program starts quicker.
- **Only what the program reaches.** A minimal `ui` program used to produce 7.85 MB of C because one reflection call pulled in every class. Now reflection, JSON and the tables follow what the program actually uses: 2.29 MB of C, and gcc needs 49 s instead of 140 s. `"stripping"` (0 none … 3 all, the default) says how much may go, `[Keep]` keeps a class or member, names a program hands to `Reflect.New("Dog")` stay by themselves, and a look-up of something that was left out says so clearly instead of failing silently.
- **Native debugging.** A debug build carries a small agent that talks to spark: breakpoints, stepping, threads, scopes, changing values, exceptions - the same panels as with the VM. Switch the engine next to the mode box from VM to native and press F5. On an ESP32 the debugger runs over the serial console, framed so it can share the wire with the program's output.
- **Libraries built once.** With `"linkage": "static"` every library and package becomes a library of its own in a user-wide cache. The second build of the `ui` sample takes 16 s instead of 100 s. `"shared"` puts them next to the program as shared libraries (Linux and Windows), checked at start.
- **Loading at run time.** `Library.Load(path)` opens a C library while the program runs and `libm.Get("cos", "float(float)")` gives a callable function; with `release:` returned memory follows fire's ownership. fire modules can be loaded the same way as plugins: their classes, units and natives join the running program, `Reflect.New` and JSON find them, and spark loads the device drivers of packages this way.

- **Smaller values for small targets.** Arrays declared with an element type (`int[8] samples[]`, `float a[]`, `bool flags[]`) now hold only that type - in the VM and natively, where they are packed: one C number per element instead of a 16-byte value, so `int[8] a[100000]` takes 100 KB instead of 1.6 MB. `#intwidth 32` makes `int` a 32-bit number, and together with `#floatwidth 32` a value on a 32-bit target takes 8 bytes instead of 16 - first steps towards microcontrollers with little RAM.

The language grew along the way, too: explicit `override`, access checks at compile time, properties and inheritance for interfaces, `[NoCopy]`, `fire handover` and a setting for when global jobs run. See [the native backend](docs/topics/native-backend.html) and [native code](docs/language/18-native-code.html) in the docs.
